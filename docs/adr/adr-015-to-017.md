# ADR-015: Row-Level Tenant Isolation Over Schema-per-Tenant

## Status
Accepted

## Date
2025-03-01

## Context
Multi-tenancy requires isolating one organization's data from another's. Two common approaches: schema-per-tenant (each tenant gets its own PostgreSQL schema) and row-level isolation (a `tenant_id` column on every shared table, filtered in queries).

## Decision
Row-level isolation via `tenant_id` UUID on all significant models, filtered by a custom `TenantQuerySet.for_tenant()` manager.

## Rationale
Schema-per-tenant breaks at scale:
- PostgreSQL connection pools are per-database, not per-schema. 100 tenants × 10 connections = 1,000 connections against PostgreSQL's default limit of 100.
- Django migrations must run against every schema separately — deployment time scales linearly with tenant count.
- Cross-tenant analytics (platform-level reporting) require federation across schemas.

Row-level filtering with indexed `tenant_id` columns:
- Scales to thousands of tenants on shared infrastructure
- Single migration deployment touches all tenants simultaneously
- One connection pool serves all tenants
- Platform-level queries (superuser) simply omit the `for_tenant()` filter

The enforcement mechanism is a custom `TenantManager` whose `for_tenant()` is called in every view via `get_tenant_from_request()`. This is not foolproof — a developer can bypass it by calling `Model.objects.all()` directly. Enforcement is supplemented by code review and a custom linter rule that flags unscoped querysets in view files.

## Consequences
A bug that accidentally omits `for_tenant()` would expose cross-tenant data. This risk is accepted and mitigated by: required code review, structured logging of every query's tenant context, and a quarterly security review of all views that touch tenant-scoped models.

# ADR-016: Kafka After Postgres (Transactional Outbox Lite)

## Status
Accepted

## Date
2025-03-01

## Context
Audit events need to reach Kafka for downstream consumers (risk engine via streaming, external integrations, multi-region replication). Two patterns: write to Kafka first then PostgreSQL, or write to PostgreSQL first then publish to Kafka.

## Decision
Write to PostgreSQL first. Publish to Kafka after successful DB write, from the same Celery task.

## Rationale
PostgreSQL is the source of truth. If we write to Kafka first and the DB write fails, we've published an event that doesn't exist in the ledger — a phantom event in the stream.

Writing to PostgreSQL first guarantees the record exists before it's published. If Kafka is down, the event is still recorded in the audit ledger. When Kafka recovers, a backfill job can replay missed events from PostgreSQL.

This is "transactional outbox lite" — it's not a true transactional outbox (which would use Debezium CDC to read the Postgres WAL and publish atomically). The risk is: if the process crashes between the DB write and the Kafka publish, the event is in the DB but not in Kafka. At Phase 5 scale, this is acceptable. True CDC outbox is Phase 6+.

## Consequences
A small window exists where a recorded audit event has not yet been published to Kafka. Downstream consumers that depend on Kafka for real-time processing may see events slightly late. This is acceptable because: (a) the risk engine runs synchronously via Celery after the DB write regardless, (b) Kafka is for durable streaming to external consumers, not primary risk scoring.

# ADR-017: SDK as a Monorepo Package with Zero Django Dependency

## Status
Accepted

## Date
2025-03-01

## Context
The SDK must be installable by any Python service — FastAPI services, plain scripts, other Django projects, AI agent frameworks. It cannot require Django.

## Decision
`sentinel-sdk` lives in `sdk/` in the monorepo as a standalone Python package. Its only dependencies are `httpx` (HTTP client) and `structlog` (logging). No Django, no DRF, no Celery.

## Rationale
If the SDK imported from `sentinel.audit` or any Django app, installing it would pull in Django, DRF, and the entire application stack. A data science team building an AI agent can't be required to install Django just to send audit events.

The monorepo placement (not a separate repo) is correct because: the SDK's event type list must stay in sync with the backend's `AuditEventType` enum; a breaking API change needs to be reflected in both simultaneously. A monorepo makes this a single PR.

## Consequences
SDK releases require manual version bumping in `sdk/pyproject.toml`. When the API event schema changes, the SDK's docstring listing available event types must be updated manually (not auto-generated from the backend enum). Acceptable for Phase 5; auto-generation from OpenAPI schema is Phase 6+.
